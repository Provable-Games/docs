# Budokan: Key Functions

This section details the primary functions exposed by the Budokan tournament system and its core data structures.

## Component Architecture

Budokan is built by composing reusable Cairo components from the open-source [game-components](https://github.com/Provable-Games/game-components) library:

| Component | Purpose |
|-----------|---------|
| **PrizeComponent** | Prize pool management, ERC20/ERC721 deposits, distribution, and claims |
| **EntryFeeComponent** | Entry fee collection, share splitting (creator, refund, protocol fee, prize pool), and payouts |
| **LeaderboardComponent** | Score submission, ranking, and position tracking with hooks |
| **RegistrationComponent** | Entry tracking, entry counts, and ban management |
| **EntryRequirementComponent** | Entry gating via token ownership, tournament qualification, or [extension validators](/budokan/guide/create/entry-requirements#extension-validators) |

These components are **not Budokan-specific** — they are general-purpose building blocks from the [Metagame Extensions](/embeddable-game-standard/reference/metagame-extensions) package. Anyone can compose them to build their own tournament or competition system with custom prize logic, entry fee handling, or scoring rules.

For example, you could build a platform that uses the same `PrizeComponent` and `LeaderboardComponent` but with entirely different entry mechanics, or extend the `EntryFeeComponent` with a custom distribution strategy.

## IBudokan Interface

Signatures match the deployed mainnet contract, which was upgraded on 14 October 2026.

### `create_tournament`
```cairo
fn create_tournament(
    ref self: TState,
    creator_rewards_address: ContractAddress,
    metadata: Metadata,
    schedule: Schedule,
    game_config: GameConfig,
    entry_fee: Option<EntryFeeKind>,
    entry_requirement: Option<EntryRequirement>,
    leaderboard_config: LeaderboardConfig,
    max_entries: u32,
) -> Tournament;
```
**Purpose:** Create a tournament. A tournament with an entry fee also mints a creator token to `creator_rewards_address`. That token receives any prize positions nobody filled. A free tournament mints no creator token: `creator_token_id` is `0`, and `creator_rewards_address` is unused.

**Parameters:**
- `creator_rewards_address`: Receives the creator token when there is an entry fee.
- `metadata`: Name and description.
- `schedule`: Delay-based schedule. See [Schedule](#schedule) and its limits.
- `game_config`: The game, its settings id, and whether entry tokens are soulbound or sponsored.
- `entry_fee`: Optional. Either Budokan's built-in ERC20 fee (`EntryFeeKind::BuiltIn`) or an external fee extension (`EntryFeeKind::Extension`).
- `entry_requirement`: Optional gate: token ownership or an [extension validator](/budokan/guide/create/entry-requirements).
- `leaderboard_config`: Score order, and whether the game must be over before a score counts.
- `max_entries`: Caps the field at this many entries (`0` = uncapped). Once the cap is filled and every entry has a ranked score, the tournament finishes early instead of waiting for its schedule. Set it whenever the field is exact, such as an invite list or fixed roster times entries per player.

**Returns:** the `Tournament` struct.

### `enter_tournament`
```cairo
fn enter_tournament(
    ref self: TState,
    tournament_id: u64,
    player_address: Option<ContractAddress>,
    qualifier: Option<ContractAddress>,
    qualification: Option<QualificationProof>,
    entry_fee_pay_params: Option<Span<felt252>>,
) -> (felt252, u32);
```
**Purpose:** Enter a tournament. This mints a game token and pays the entry fee from the caller.

**Parameters:**
- `player_address`: Who receives the game token. `None` means the caller. When there is an entry requirement, a different recipient is honoured only if the caller is the qualifier.
- `qualifier`: Who qualifies for entry. `None` means the caller. Token gates check `owner_of`; extension validators receive this address and verify the proof themselves.
- `qualification`: Optional proof: an NFT token id, or extension-specific data.
- `entry_fee_pay_params`: Required for `EntryFeeKind::Extension` fees. Otherwise pass `None`.

**Returns:** `(game token id, entry number)`.

:::warning
Use one mint path per tournament per transaction. Several single entries in one transaction collide at mint nonce zero. For several recipients, use `enter_tournament_for_recipients`.
:::

### `enter_tournament_for_recipients`
```cairo
fn enter_tournament_for_recipients(
    ref self: TState,
    tournament_id: u64,
    recipients: Array<TournamentRecipientParams>,
) -> Array<felt252>;
```
**Purpose:** Enter one tournament for many recipients in a single transaction. With the built-in fee, the caller pays N × fee in one transfer. Returns the token ids in recipient order. Each `TournamentRecipientParams` has the same `player_address`, `qualifier` and `qualification` options as `enter_tournament`.

### `claim_reward`
```cairo
fn claim_reward(
    ref self: TState,
    tournament_id: u64,
    reward_type: RewardType,
);
```
**Purpose:** The single settlement entrypoint after a tournament is finalized. It pays sponsored prizes and every slice of the entry-fee pool. The recipient is worked out on-chain: the leaderboard winner for a position, the creator token for an unfilled position, and the declared recipients for the creator share and protocol fee. Anyone can call it.

**Parameters:**
- `reward_type`: `Prize(PrizeClaim)` or `EntryFee(EntryFeeClaim)`. See [RewardType](#rewardtype).

---

### `add_prize`
```cairo
fn add_prize(
    ref self: TState,
    tournament_id: u64,
    prize: Prize,
    position: Option<u32>,
) -> u64;
```
**Purpose:** Sponsor a prize. `Prize::Token` deposits ERC20 or ERC721 tokens. An ERC20 prize can be paid to a single position or spread over several with a `Distribution`. `Prize::Extension` forwards its config to an `IPrizeExtension` contract, which owns its own payout rules.

**Returns:** the new `prize_id`. Read the full payload from the `PrizeAdded` event.

fn ban_entry(
    ref self: TState,

**Purpose:** Permissionlessly ban an entry that no longer meets the tournament's extension validator. The validator confirms the ban through `should_ban`. See [Entry Requirements: Banning Mechanism](/budokan/guide/create/entry-requirements#banning-mechanism).

### View Functions

```cairo
fn total_tournaments(self: @TState) -> u64;
fn tournament(self: @TState, tournament_id: u64) -> Tournament;
fn tournament_game_address(self: @TState, tournament_id: u64) -> ContractAddress;
fn current_phase(self: @TState, tournament_id: u64) -> Phase;
fn max_entries(self: @TState, tournament_id: u64) -> u32;
fn is_token_registered(self: @TState, tournament_id: u64, token_id: felt252) -> bool;
fn tournament_distribution_shares(self: @TState, tournament_id: u64) -> Array<u16>;
fn prize_distribution_shares(self: @TState, prize_id: u64) -> Array<u16>;
fn schedule_limits(self: @TState) -> ScheduleLimits;
```

- `tournament_game_address`: Just the game address, in one storage read. Returns zero for an unknown id.
- `current_phase`: Accounts for early finish. Once every entry has a ranked score, it reports `Finalized` early: during the submission window for any tournament, and during play for a full, capped one.
- `is_token_registered`: Whether a game token is entered in a given tournament. Validators use it to qualify players by past participation.
- `tournament_distribution_shares` / `prize_distribution_shares`: The full basis-point array for `Distribution::Custom`. Both `tournament()` and the `PrizeAdded` event carry an empty `Custom` to stay small.
- `schedule_limits`: The allowed range for each schedule duration. See [Schedule](#schedule).

:::tip
For batched queries, use the **BudokanViewer** contract or the [SDK](/budokan/sdk) instead of calling these one by one.
:::

## Data Structures

### Schedule

Phases are worked out from delays relative to the creation timestamp:

```cairo
pub struct Schedule {
    pub registration_start_delay: u32,
    pub registration_end_delay: u32,
    pub game_start_delay: u32,
    pub game_end_delay: u32,
    pub submission_duration: u32,
}
```

If a tournament is created at time `T`:
- Registration opens at `T + registration_start_delay` and closes at `T + registration_end_delay`.
- The game starts at `T + game_start_delay` and ends at `T + game_start_delay + game_end_delay`.
- Submission ends `submission_duration` after the game ends.

A registration delay of `0` means there is no separate registration period.

Each duration must fall within the owner-set `schedule_limits()`. On mainnet these are currently:

| Duration | Minimum | Maximum |
| --- | --- | --- |
| Registration period | 1 hour | 90 days |
| Tournament length (`game_end_delay`) | 1 hour | 365 days |
| Submission period | 1 hour | 90 days |

### EntryFeeKind and EntryFee

```cairo
pub enum EntryFeeKind {
    BuiltIn: EntryFee,
    Extension: ExtensionConfig,   // an IEntryFeeExtension decides collection and payout
}

pub struct EntryFee {
    pub token_address: ContractAddress,
    pub amount: u128,
    pub tournament_creator_share: u16,  // basis points, paid to the tournament creator
    pub game_fee_share: u16,            // basis points; must be 0 for current game tokens
    pub refund_share: u16,              // basis points returned to each entry's owner
    pub distribution: Distribution,     // how the prize pool splits across positions
    pub distribution_count: u32,        // paid positions (0 = sized to the leaderboard)
}
```

Budokan's **protocol fee** is set by the owner (currently 5%, 500 bps) and fixed for each tournament when it's created. The prize pool is what remains after the creator share, refund share and protocol fee.

Current game tokens have no game-fee recipient, so `game_fee_share` must be `0`. Creation reverts otherwise.

`Distribution` is one of `Uniform`, `Linear(weight)`, `Exponential(10 × k)`, `Geometric(a, b)`, `Tiered(TieredConfig)` or `Custom(shares)`. See [Distribution Strategies](/budokan/guide/create/entry-fees#distribution-strategies).
